# v1.0.0 release acceptance contract

Agent Team Engineering `v1.0.0` is accepted only when its portable independent-writer authority, host lifecycle safety, explicit instance migration, public adoption path, supply chain, and remote release identity all pass together.

This document is the normative checklist, not a claim that a candidate branch has already passed it. A gate becomes complete only when the exact candidate or release commit has the required command output, immutable digest, and remote URL or artifact. Never infer PR, CI, tag, GitHub Release, anonymous-install, or external-system completion from a version file, changelog heading, local test, or this document.

The machine-readable candidate companion is [`acceptance/v10-host-native-conformance.json`](../../acceptance/v10-host-native-conformance.json). Its source status remains `PRE_RELEASE` even after local and dedicated-SCM gates pass: a source commit cannot truthfully contain future PR, tag, workflow, GitHub Release, artifact-download, or anonymous-install facts about itself. The tag workflow therefore generates a separate `TAG_WORKFLOW_EVIDENCE` artifact with `status=PARTIAL` and `release_status=NOT_PUBLISHED`. It records only facts knowable during that run and keeps PR/publication gates `NOT_RUN`; it can never declare its own run, artifact upload, GitHub Release, or anonymous installation successful.

After the tag workflow and GitHub Release exist, run the independently staged [`tools/release_publication.py`](../../tools/release_publication.py) finalizer. It performs read-only live GitHub verification, downloads and verifies the exact workflow artifact and `SHA256SUMS`, then performs a fresh exact-tag installation cloned over unauthenticated public HTTPS. Only that post-publication process may write an external `FINAL_RELEASE_INDEX` with `status=ACCEPTED` and `release_status=RELEASED`. The final index is deliberately written outside the tagged source and must not be committed back into, or used to modify, the immutable `v1.0.0` tree.

The immutable recovery baseline is annotated `v0.9.0` at `a286cfadbfb6f387a4f1fb94c244f57d4dd089e6`.

## Product and authority scope

The release must preserve the Host-native Agent Team Factory product boundary:

- Markdown, JSON, Skills, Git history, and digest locks remain the portable team authority;
- host packages remain derived projections at their recorded evidence tiers;
- the Managed controller remains optional and has one source-writing `builder`;
- WriterTopology is `DESIGN_ONLY` authority, not a scheduler or execution grant;
- team creation, host projection, native host activation, external SCM, merge, release, and deployment remain distinct authorization scopes;
- no Factory path automatically merges, releases, or deploys user code.

The offline writer-authority validator checks local document Schema, semantics, digests, and cross-document bindings. It must return both `automatic_execution: false` and `identity_or_signature_verified: false`. It does not authenticate an approval actor, verify a digital signature, or turn a document into production identity authority.

- a persistent `empty-regular-file-v1` operation guard with its empty-content digest;
- deterministic per-file stages, the declared metadata scratch `.agent-team/.host-lifecycle.json.stage`, and one plan-digest-bound random empty initial-apply intent under `.agent-team/.host-apply.intent-<32-hex>`;
- no overwrite of projected files, no symlink traversal, exact source SHA-256 recheck, and fail-closed baseline drift handling;
- cooperating-process serialization with POSIX `fcntl`, without claiming protection from root, the kernel, the filesystem, storage failure, or non-cooperating privileged writers;
- planning-time absence of the metadata stage and every apply-intent-prefix entry, plus exact same-plan recovery across the guard-fsync, initial-intent/metadata-transition, `APPLYING`, and staged-file crash windows;
- explicit prior guard/tombstone identity and a newly confirmed deletion effect before an old tombstone may be removed;
- read-only `uninstall-preview`, exact-digest `ACTIVE → UNINSTALLING → UNINSTALLED` recovery, and idempotent tombstone replay;
- scratch creation/deletion reported in both effect lists for active removal, with the scratch absent after success;
- unchanged managed-file and inode checks before unlink, persistent guard and tombstone retention, and `directories_removed=false`;
- v0.9 unexecuted plans rejected until regenerated, previewed, and reconfirmed;
- v0.9 locks reported only as `LEGACY_UNBOUND`, with automatic destructive uninstall disabled and manual reconciliation required.

The host catalog, OpenClaw/Hermes isolated install evidence, Codex/Claude export evidence, Multica experimental-plan boundary, custom Multica License treatment, and Leda `research-unknown` status must not be overstated.

## Instance migration and recovery gates

The `0.9.0 → 1.0.0` Team Instance migration must preserve user-edited seeded files and must not migrate old runtime approvals. ## Disposable Runner and external SCM gates

Disposable Runner evidence must come from an exact-candidate GitHub-hosted ephemeral worker and include all declared trials, environment facts, sanitized evidence, and cleanup results. The run must have no inherited production secrets, Docker Socket, PVE/NAS path, production mount, or residue. A local Host Runner is not equivalent evidence.

External GitHub SCM evidence must be produced in a dedicated authorized evidence repository with minimum-permission identity and must bind the exact v1 implementation commit. It must show:

1. a first run creates the expected feedback Issue, proposal branch/commit, and unmerged Draft PR;
2. replay with the same idempotency identity creates no duplicate object;
3. first-run and replay reports retain identical trusted external references and provider IDs;
4. no merge, release, deployment, settings change, or unrelated repository write occurs;
5. evidence files pass schema, trust-boundary, history, and protected-implementation checks.

If an evidence-protected SCM path changed after the last live fixture, prior evidence is stale. Each candidate uses a proposal branch and evidence-file path derived from the complete Factory commit, so a new candidate never overwrites or adopts an older candidate's disposable proposal. The two sanitized SCM reports must be recorded together in one evidence-only commit whose sole parent is the exact implementation commit exercised by both runs; that commit may change exactly those two report paths. The candidate aggregate and both SCM reports are themselves protected, and every later protected-path change fails release audit. Release audit must fail closed until a fresh authorized first-run/replay fixture is recorded. Do not reuse v0.8 or v0.9 evidence merely because its JSON still validates.

A source document cannot embed the future commit hash or remote URLs of the commit that contains it. Those identities belong in immutable PR/check/tag/Release records or a separately published release evidence record. Their absence means the remote gate is not yet accepted.

### Two-stage machine evidence

The release-evidence Schema has two intentionally non-interchangeable document kinds:

| Kind | May claim | Must not claim |

| `TAG_WORKFLOW_EVIDENCE` | exact annotated tag object and peeled commit; local/tag commands; bundled v10, SBOM, provenance and SCM report digests | its own workflow completion, uploaded artifact identity/download, GitHub Release, anonymous install, `ACCEPTED` or `RELEASED` |

The finalizer accepts a small external JSON request containing repository/release/commit, PR number/head and complete required-check identity, external technical-review identity, GitHub owner-approval identity, accepted-main commit and its complete required-check identity, tag-workflow URL and GitHub Release URL. Those are claims to verify, not proof. It independently requeries each required check's Actions run and binds the immutable workflow path, event, exact commit, job/check-suite/run identities, App, repository and URL before accepting the result. It must also prove that the merged PR targeted this repository's `main`, the accepted commit is the live `refs/heads/main` tip, and both requested check sets equal effective `main` protection. It then downloads the strict technical-review JSON from the exact private workflow run, clones public Git without inherited credentials, reconstructs the complete tracked `v0.9.0..reviewed-head` repository diff without a path filter, rebuilds the canonical review rubric and pre-sealing review input, and requires all three SHA-256 bindings plus head/tree/workflow commit/runtime/`PASS` decision to agree. It also verifies the exact-head GitHub User `APPROVED` review. It uses minimum read-only GitHub access only for GET requests, requires one non-expired exact-name tag artifact belonging to the exact tag run, and downloads that artifact rather than trusting metadata. Artifact ID and both API URLs, digest, creation chronology, bundle file set, every SHA256SUMS entry, embedded tag evidence, workflow run/attempt, annotated tag name/object/peeled commit and five required asset digests must agree. ## Unauthenticated public-HTTPS exact-tag installation gate

Run this gate from an independently controlled release worker without a pre-existing checkout. The machine record proves that caller credentials are not inherited by the candidate subprocess environment and that the Git clone uses unauthenticated public HTTPS; it does not prove that the operating-system user or machine has no credentials elsewhere.

1. clone the public repository over unauthenticated HTTPS;
2. fetch and verify annotated tag `v1.0.0` and its peeled commit against the accepted release record;
3. check out that exact tag with a clean worktree;
4. run Factory install into an absent directory, `factory verify`, and Doctor;
5. create and validate a portable team;
6. plan, preview, confirm, apply, verify, preview removal, uninstall, and idempotently verify one disposable host projection without credentials or live host writes;
7. validate the canonical WriterTopology chain and confirm both false boundary fields;
8. record commands, exit codes, environment, commit/tag IDs, artifact digests, and the exact isolation/observation boundary; do not claim that unobserved writes outside the worker workspace did not occur.

Testing a local path, authenticated clone, branch head, lightweight tag, or simulated tag does not satisfy this gate.

The reference finalizer completes all token-bearing GitHub reads first, then starts `tools/anonymous_release_worker.py` through `/usr/bin/setpriv` under a random numeric UID with no local account, no supplementary groups, no capabilities, and `no_new_privileges`. Before it runs candidate code, that worker must prove `/proc/<credential-parent-pid>/environ` is unreadable. Inside that boundary it uses a literal minimal environment allowlist, disables global/system Git credential configuration and terminal prompting, clones public HTTPS with `--no-local`, verifies the tag object and peeled commit, and performs Factory install/verify/Doctor, portable-team generation, one disposable generic host projection through replay-safe uninstall, and complete WriterTopology validation. A caller-supplied success statement is not accepted as a substitute.

This is a transport, credential-process, environment-inheritance, and resource-containment boundary, not a complete network sandbox or global write monitor. A transient systemd cgroup limits memory, swap, CPU, process count, file output, runtime and the private temporary filesystem; it also terminates the complete remaining cgroup when the worker stops. The random UID cannot read the credential-bearing parent process, but it may still reach the network and resources not denied by the systemd filesystem policy. For stronger release isolation, run the entire finalizer on a dedicated credential-free disposable Runner with separate kernel and network isolation; the schema deliberately keeps `same_uid_filesystem_isolated=false`, `write_isolation=false`, and `external_writes_verified=false` for the reference worker.

## Acceptance record rule

The release owner may declare `v1.0.0` accepted only when one external `FINAL_RELEASE_INDEX` maps every gate above to the same accepted commit/tag and contains actual command results, artifact digests, download evidence, and remote URLs. Treat it as an unsigned observation index: archive it together with the original artifacts and rerun the finalizer's read-only checks when authenticity matters. The machine representation uses exact `PASS`, `FAIL`, or `NOT_RUN`; never replace missing evidence with prose such as “expected,” “should pass,” or “verified elsewhere.” Any `FAIL`, `NOT_RUN`, stale external fixture, identity mismatch, undownloaded artifact, missing URL, or missing rollback evidence blocks release completion. The tag-workflow artifact remains an immutable partial input and must never be relabeled or edited into the final index.

## Rollback

The immutable rollback baseline is `v0.9.0`. Keep every v0.9→1.0 instance recovery bundle and every v1-before-rollback rescue bundle until owner acceptance and retention policy permit disposal. Reconcile external Issue/branch/PR effects before retry or rollback. For host projections, run verify and uninstall-preview first; only a proposal-bound v1 lock may use automatic exact-digest uninstall. Preserve and manually reconcile every `LEGACY_UNBOUND` v0.9 installation. Never move a tag, delete a lock or tombstone to force progress, reuse an old approval after topology drift, or treat rollback as authorization to merge or deploy.
