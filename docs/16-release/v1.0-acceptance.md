# v1.0.0 release acceptance contract

Agent Team Engineering `v1.0.0` is accepted only when its portable independent-writer authority, host lifecycle safety, explicit instance migration, public adoption path, supply chain, and remote release identity all pass together.

This document is the normative checklist, not a claim that a candidate branch has already passed it. A gate becomes complete only when the exact candidate or release commit has the required command output, immutable digest, and remote URL or artifact. Never infer PR, CI, tag, GitHub Release, anonymous-install, or external-system completion from a version file, changelog heading, local test, or this document.

The machine-readable candidate companion is [`acceptance/v10-host-native-conformance.json`](../../acceptance/v10-host-native-conformance.json). Its source status remains `PRE_RELEASE` even after local and dedicated-SCM gates pass: a source commit cannot truthfully contain future PR, tag, workflow, GitHub Release, artifact-download, or anonymous-install facts about itself. The tag workflow therefore generates a separate `TAG_WORKFLOW_EVIDENCE` artifact with `status=PARTIAL` and `release_status=NOT_PUBLISHED`. It records only facts knowable during that run and keeps PR/publication gates `NOT_RUN`; it can never declare its own run, artifact upload, GitHub Release, or anonymous installation successful.

After the tag workflow and GitHub Release exist, run the independently staged [`tools/release_publication.py`](../../tools/release_publication.py) finalizer. It performs read-only live GitHub verification, downloads and verifies the exact workflow artifact and `SHA256SUMS`, then performs a fresh anonymous exact-tag installation. Only that post-publication process may write an external `FINAL_RELEASE_INDEX` with `status=ACCEPTED` and `release_status=RELEASED`. The final index is deliberately written outside the tagged source and must not be committed back into, or used to modify, the immutable `v1.0.0` tree.

The immutable recovery baseline is annotated `v0.9.0` at `a286cfadbfb6f387a4f1fb94c244f57d4dd089e6`.

## Product and authority scope

The release must preserve the Host-native Agent Team Factory product boundary:

- Markdown, JSON, Skills, Git history, and digest locks remain the portable team authority;
- host packages remain derived projections at their recorded evidence tiers;
- the Managed controller remains optional and has one source-writing `builder`;
- WriterTopology is `DESIGN_ONLY` authority, not a scheduler or execution grant;
- team creation, host projection, native host activation, external SCM, merge, release, and deployment remain distinct authorization scopes;
- no Factory path automatically merges, releases, or deploys user code.

The offline writer-authority validator checks local document Schema, semantics, digests, and cross-document bindings. It must return both `automatic_execution: false` and `identity_or_signature_verified: false`. It does not authenticate an approval actor, verify a digital signature, or turn a document into production identity authority.

## Host lifecycle safety gates

Host plan and install-lock `1.1.0` must bind the complete proposal and demonstrate:

- a persistent `empty-regular-file-v1` operation guard with its empty-content digest;
- deterministic per-file stages plus the only declared metadata scratch, `.agent-team/.host-lifecycle.json.stage`;
- no overwrite of projected files, no symlink traversal, exact source SHA-256 recheck, and fail-closed baseline drift handling;
- cooperating-process serialization with POSIX `fcntl`, without claiming protection from root, the kernel, the filesystem, storage failure, or non-cooperating privileged writers;
- exact same-plan recovery across the guard-fsync/`APPLYING` and staged-file crash windows;
- explicit prior guard/tombstone identity and a newly confirmed deletion effect before an old tombstone may be removed;
- read-only `uninstall-preview`, exact-digest `ACTIVE → UNINSTALLING → UNINSTALLED` recovery, and idempotent tombstone replay;
- scratch creation/deletion reported in both effect lists for active removal, with the scratch absent after success;
- unchanged managed-file and inode checks before unlink, persistent guard and tombstone retention, and `directories_removed=false`;
- v0.9 unexecuted plans rejected until regenerated, previewed, and reconfirmed;
- v0.9 locks reported only as `LEGACY_UNBOUND`, with automatic destructive uninstall disabled and manual reconciliation required.

The host catalog, OpenClaw/Hermes isolated install evidence, Codex/Claude export evidence, Multica experimental-plan boundary, custom Multica License treatment, and Leda `research-unknown` status must not be overstated.

## Instance migration and recovery gates

Factory `1.0.0` must explicitly accept `0.9.0` and every earlier declared supported source version. For each source, tests must prove plan, external recovery bundle, managed-file transition, target lock commit, interruption recovery, and deliberate rollback behavior.

The `0.9.0 → 1.0.0` Team Instance migration must preserve user-edited seeded files and must not migrate old runtime approvals. It must not be described as upgrading a v0.9 host-install plan or legacy host lock. Lifecycle journal, recovery bundle, writer quiescence, audit, lease, outbox, permissions, and fail-closed drift requirements remain mandatory.

## Public, documentation, and Skill gates

- English and Chinese README first screens explain the input, portable output, optional host projection, evidence tiers, Managed boundary, and direct AI start path.
- `AI-START.md` leads an adopter through read-only discovery, at most three high-impact questions, recommendation, separate team and host previews, two exact confirmations, validation, and a usable first request.
- `AI-BOOTSTRAP.md` routes maintainers to the exact authority surface and this acceptance contract without calling a candidate branch a release.
- Factory `1.0.0`, contract `1.0.0`/`1.1.0`, host-plan `1.1.0`, legacy v0.9, and historical v0.9 release semantics are clearly distinguished.
- Root and bundled Skills pass strict frontmatter and content validation and carry the same offline identity, no-execution, no-merge, and no-deploy boundaries.
- All local documentation links resolve, and public examples use commands implemented by the exact candidate.

## Reproducible local gates

Run from a clean checkout of the exact candidate commit and retain full command output:


Also require:

- root and bundled Skill quick validation;
- Codex and Claude plugin/marketplace manifest validation;
- deterministic simulation, instance smoke, context-team smoke, host lifecycle smoke, and writer-authority negative cases;
- secret scanning over `v0.9.0..candidate`, license review, version consistency, SPDX SBOM consistency, and source-provenance consistency;
- no-history human/AI adoption and maintenance handoff that reaches the correct stop points without chat history;
- a clean Git worktree before any release-audit evidence is accepted.

A local simulated tag from `tools/release-smoke.sh` proves the code path only. It is not the remote annotated tag, tag workflow, GitHub Release, or anonymous network installation.

## Disposable Runner and external SCM gates

Disposable Runner evidence must come from an exact-candidate GitHub-hosted ephemeral worker and include all declared trials, environment facts, sanitized evidence, and cleanup results. The run must have no inherited production secrets, Docker Socket, PVE/NAS path, production mount, or residue. A local Host Runner is not equivalent evidence.

External GitHub SCM evidence must be produced in a dedicated authorized evidence repository with minimum-permission identity and must bind the exact v1 implementation commit. It must show:

1. a first run creates the expected feedback Issue, proposal branch/commit, and unmerged Draft PR;
2. replay with the same idempotency identity creates no duplicate object;
3. first-run and replay reports retain identical trusted external references and provider IDs;
4. no merge, release, deployment, settings change, or unrelated repository write occurs;
5. evidence files pass schema, trust-boundary, history, and protected-implementation checks.

If an evidence-protected SCM path changed after the last live fixture, prior evidence is stale. Release audit must fail closed until a fresh authorized first-run/replay fixture is recorded. Do not reuse v0.8 or v0.9 evidence merely because its JSON still validates.

## Pull request and continuous-integration gates

Before merge, record the PR URL, exact head commit, independent review decision, and URLs for every required check. The approving reviewer must be a different GitHub human `User` with `COLLABORATOR`, `MEMBER`, or `OWNER` association; a bot, workflow identity, untrusted drive-by review, author-controlled alternate spelling, local Agent report, or PR comment is not an independent approval. The exact PR head must pass the repository validation workflow and, where applicable, disposable Runner conformance. No unresolved blocking review or skipped required check is acceptable.

After merge, record the exact `main` commit and its passing workflow URL. The merged-main commit, not only the pre-merge head, must pass validation, tests, audit, simulation, instance/context smoke, cold start, and simulated release smoke. Any post-review change requires the relevant gates again.

GitHub Actions used by release and Runner evidence must remain pinned by full commit SHA. The `actions/upload-artifact` step must use the reviewed v7.0.1 commit `043fb46d1a93c77aae656e7c1c64a875d1fc6a0a` and its Node 24 runtime; acceptance must not contain the earlier Node 20 deprecation warning.

## Tag, GitHub Release, and artifact gates

Only after the exact merged-main commit passes all prior gates may maintainers create annotated tag `v1.0.0`. Record and verify:

- tag object type `tag`, immutable tag-object ID, peeled commit, trusted creator, and exact match to the accepted `main` commit;
- passing `release-verify.yml` URL for the exact tag, including external-evidence audit and release smoke;
- GitHub Release URL bound to the same tag and commit;
- uploaded release-evidence artifact identity, retention, hashes, and successful download/inspection;
- exact SBOM and source-provenance digests matching the tagged tree;
- no moved/recreated tag and no artifact rebuilt from another commit.

A source document cannot embed the future commit hash or remote URLs of the commit that contains it. Those identities belong in immutable PR/check/tag/Release records or a separately published release evidence record. Their absence means the remote gate is not yet accepted.

### Two-stage machine evidence

The release-evidence Schema has two intentionally non-interchangeable document kinds:

| Kind | May claim | Must not claim |
|---|---|---|
| `TAG_WORKFLOW_EVIDENCE` | exact annotated tag object and peeled commit; local/tag commands; bundled v10, SBOM, provenance and SCM report digests | its own workflow completion, uploaded artifact identity/download, GitHub Release, anonymous install, `ACCEPTED` or `RELEASED` |
| `FINAL_RELEASE_INDEX` | exact PR head/checks, independent approved review, merged-main workflow, tag workflow, artifact ID/URL/digest/retention and download verification, GitHub Release, anonymous exact-tag install, and every gate `PASS` | any missing, failed, inferred, self-reported, cross-commit or undownloaded gate |

The finalizer accepts a small external JSON request containing only repository/release/commit, PR number/head/check URL, independent reviewer/review URL, merged-main workflow URL, tag-workflow URL and GitHub Release URL. Those are claims to verify, not proof. It uses a read-only GitHub token only for GET requests, checks every returned URL and identity, requires one non-expired exact-name artifact belonging to the exact tag run, and downloads it rather than trusting metadata. Artifact digest, bundle file set, every SHA256SUMS entry, embedded tag evidence, workflow run/attempt, annotated tag object, peeled commit and five required asset digests must agree.

The five digest-bound assets are:

- `acceptance/v10-host-native-conformance.json`;
- `sbom/agent-team-engineering.spdx.json`;
- `supply-chain/source-provenance.json`;
- `acceptance/github-scm-v10-first-run.json`;
- `acceptance/github-scm-v10-replay.json`.

The final external index records the upload-artifact ID, API URL, archive-download URL, service digest, created/expiry timestamps, derived retention days, actual download timestamp and archive digest, tag-evidence digest, and SHA256SUMS digest. Missing URL, non-approved review, wrong head/main/tag commit, failed workflow, absent Release, expired or duplicate artifact, digest mismatch, missing checksum, skipped download, authenticated/local clone substitution, or any `FAIL`/`NOT_RUN` refuses finalization.

A request template is intentionally kept outside the tagged tree because it contains post-tag facts. From an independently controlled release workstation or workflow, create it with this exact non-secret shape:

Run the finalizer with an output path outside every Factory checkout:

```bash
GITHUB_TOKEN='<read-only-token>' python3 /path/to/reviewed-finalizer/tools/release_publication.py \
  --request /external/release-evidence/v1.0.0-request.json \
  --output /external/release-evidence/v1.0.0-final-release-index.json
```

Do not place the token in the request, shell history, output, or repository. The token must have only the minimum read access needed for this repository's PR/review, Actions artifact, tag and Release metadata. The finalizer strips token-like environment variables before anonymous cloning and runs with terminal credential prompting disabled.

## Anonymous exact-tag installation gate

From an environment without maintainer credentials or a pre-existing checkout:

1. clone the public repository over anonymous HTTPS;
2. fetch and verify annotated tag `v1.0.0` and its peeled commit against the accepted release record;
3. check out that exact tag with a clean worktree;
4. run Factory install into an absent directory, `factory verify`, and Doctor;
5. create and validate a portable team;
6. plan, preview, confirm, apply, verify, preview removal, uninstall, and idempotently verify one disposable host projection without credentials or live host writes;
7. validate the canonical WriterTopology chain and confirm both false boundary fields;
8. record commands, exit codes, environment, commit/tag IDs, artifact digests, and zero external side effects.

Testing a local path, authenticated clone, branch head, lightweight tag, or simulated tag does not satisfy this gate.

The reference finalizer executes this gate itself after removing token/password/secret-like environment variables, disabling global/system Git credential configuration and terminal prompting, cloning public HTTPS with `--no-local`, and verifying the tag object and peeled commit. It then performs Factory install/verify/Doctor, portable-team generation, one disposable generic host projection through replay-safe uninstall, and the complete WriterTopology validation. It records `maintainer_credentials_available=false` and `external_writes=false`; a caller-supplied success statement is not accepted as a substitute.

## Acceptance record rule

The release owner may declare `v1.0.0` accepted only when one external `FINAL_RELEASE_INDEX` maps every gate above to the same accepted commit/tag and contains actual command results, artifact digests, download evidence, and remote URLs. The machine representation uses exact `PASS`, `FAIL`, or `NOT_RUN`; never replace missing evidence with prose such as “expected,” “should pass,” or “verified elsewhere.” Any `FAIL`, `NOT_RUN`, stale external fixture, identity mismatch, undownloaded artifact, missing URL, or missing rollback evidence blocks release completion. The tag-workflow artifact remains an immutable partial input and must never be relabeled or edited into the final index.

## Rollback

The immutable rollback baseline is `v0.9.0`. Keep every v0.9→1.0 instance recovery bundle and every v1-before-rollback rescue bundle until owner acceptance and retention policy permit disposal. Reconcile external Issue/branch/PR effects before retry or rollback. For host projections, run verify and uninstall-preview first; only a proposal-bound v1 lock may use automatic exact-digest uninstall. Preserve and manually reconcile every `LEGACY_UNBOUND` v0.9 installation. Never move a tag, delete a lock or tombstone to force progress, reuse an old approval after topology drift, or treat rollback as authorization to merge or deploy.
