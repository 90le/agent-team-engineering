# v1.0.0 release acceptance contract

Agent Team Engineering `v1.0.0` is accepted only when its portable independent-writer authority, host lifecycle safety, explicit instance migration, public adoption path, supply chain, and remote release identity all pass together.

This document is the normative checklist, not a claim that a candidate branch has already passed it. A gate becomes complete only when the exact candidate or release commit has the required command output, immutable digest, and remote URL or artifact. Never infer PR, CI, tag, GitHub Release, anonymous-install, or external-system completion from a version file, changelog heading, local test, or this document.

The machine-readable candidate companion is [`acceptance/v10-host-native-conformance.json`](../../acceptance/v10-host-native-conformance.json). Its source status remains `PRE_RELEASE` even after local and dedicated-SCM gates pass: a source commit cannot truthfully contain future PR, tag, workflow, GitHub Release, artifact-download, or anonymous-install facts about itself. The tag workflow therefore generates a separate `TAG_WORKFLOW_EVIDENCE` artifact with `status=PARTIAL` and `release_status=NOT_PUBLISHED`. It records only facts knowable during that run and keeps PR/publication gates `NOT_RUN`; it can never declare its own run, artifact upload, GitHub Release, or anonymous installation successful.

After the tag workflow and GitHub Release exist, run the independently staged [`tools/release_publication.py`](../../tools/release_publication.py) finalizer. It performs read-only live GitHub verification, downloads and verifies the exact workflow artifact and `SHA256SUMS`, then performs a fresh exact-tag installation cloned over unauthenticated public HTTPS. Only that post-publication process may write an external `FINAL_RELEASE_INDEX` with `status=ACCEPTED` and `release_status=RELEASED`. The final index is deliberately written outside the tagged source and must not be committed back into, or used to modify, the immutable `v1.0.0` tree.

The immutable recovery baseline is annotated `v0.9.0` at `a286cfadbfb6f387a4f1fb94c244f57d4dd089e6`.

## Product and authority scope

The release must preserve the Host-native Agent Team Factory product boundary:

- Markdown, JSON, Skills, Git history, and digest locks remain the portable team authority;
- host packages remain derived projections at their recorded evidence tiers;
- the Managed controller remains optional and has one source-writing `builder`;
- WriterTopology is `DESIGN_ONLY` authority, not a scheduler or execution grant;
- team creation, host projection, native host activation, external SCM, merge, release, and deployment remain distinct authorization scopes;
- no Factory path automatically merges, releases, or deploys user code.

The offline writer-authority validator checks local document Schema, semantics, digests, and cross-document bindings. It must return both `automatic_execution: false` and `identity_or_signature_verified: false`. It does not authenticate an approval actor, verify a digital signature, or turn a document into production identity authority.

## Host lifecycle safety gates

Host plan and install-lock `1.1.0` must bind the complete proposal and demonstrate:

- a persistent `empty-regular-file-v1` operation guard with its empty-content digest;
- deterministic per-file stages plus the only declared metadata scratch, `.agent-team/.host-lifecycle.json.stage`;
- no overwrite of projected files, no symlink traversal, exact source SHA-256 recheck, and fail-closed baseline drift handling;
- cooperating-process serialization with POSIX `fcntl`, without claiming protection from root, the kernel, the filesystem, storage failure, or non-cooperating privileged writers;
- exact same-plan recovery across the guard-fsync/`APPLYING` and staged-file crash windows;
- explicit prior guard/tombstone identity and a newly confirmed deletion effect before an old tombstone may be removed;
- read-only `uninstall-preview`, exact-digest `ACTIVE → UNINSTALLING → UNINSTALLED` recovery, and idempotent tombstone replay;
- scratch creation/deletion reported in both effect lists for active removal, with the scratch absent after success;
- unchanged managed-file and inode checks before unlink, persistent guard and tombstone retention, and `directories_removed=false`;
- v0.9 unexecuted plans rejected until regenerated, previewed, and reconfirmed;
- v0.9 locks reported only as `LEGACY_UNBOUND`, with automatic destructive uninstall disabled and manual reconciliation required.

The host catalog, OpenClaw/Hermes isolated install evidence, Codex/Claude export evidence, Multica experimental-plan boundary, custom Multica License treatment, and Leda `research-unknown` status must not be overstated.

## Instance migration and recovery gates

Factory `1.0.0` must explicitly accept `0.9.0` and every earlier declared supported source version. For each source, tests must prove plan, external recovery bundle, managed-file transition, target lock commit, interruption recovery, and deliberate rollback behavior.

The `0.9.0 → 1.0.0` Team Instance migration must preserve user-edited seeded files and must not migrate old runtime approvals. It must not be described as upgrading a v0.9 host-install plan or legacy host lock. Lifecycle journal, recovery bundle, writer quiescence, audit, lease, outbox, permissions, and fail-closed drift requirements remain mandatory.

## Disposable Runner and external SCM gates

Disposable Runner evidence must come from an exact-candidate GitHub-hosted ephemeral worker and include all declared trials, environment facts, sanitized evidence, and cleanup results. The run must have no inherited production secrets, Docker Socket, PVE/NAS path, production mount, or residue. A local Host Runner is not equivalent evidence.

External GitHub SCM evidence must be produced in a dedicated authorized evidence repository with minimum-permission identity and must bind the exact v1 implementation commit. It must show:

1. a first run creates the expected feedback Issue, proposal branch/commit, and unmerged Draft PR;
2. replay with the same idempotency identity creates no duplicate object;
3. first-run and replay reports retain identical trusted external references and provider IDs;
4. no merge, release, deployment, settings change, or unrelated repository write occurs;
5. evidence files pass schema, trust-boundary, history, and protected-implementation checks.

If an evidence-protected SCM path changed after the last live fixture, prior evidence is stale. Release audit must fail closed until a fresh authorized first-run/replay fixture is recorded. Do not reuse v0.8 or v0.9 evidence merely because its JSON still validates.

2. **Technical review:** the read-only OpenClaw reviewer `ate-3df2c143-independent-reviewer` must review the exact public security-sensitive patch using runtime `openclaw/relay/gpt-5.6-sol`. The private `90le/agent-team-v10-review-private` workflow pinned at `5dd269b0015b576bad3b85cc358d75d8ed205ed6` independently reruns deterministic gates, recomputes the public patch digest, validates the strict review input, and seals it as an artifact without model or source-repository write permission. Record `reviewer_kind=independent-ai`, exact head/tree/workflow, OpenClaw Agent/session, prompt and patch digests, the Actions run URL, and the SHA-256 of the sealed strict review JSON. In this review document, `generated_at` is the time when the external OpenClaw model completed its review; it must precede creation and start of the later sealing workflow. The artifact `created_at` is the separate time when that workflow sealed the already-generated review. The JSON decision must be `PASS`. Both external review generation and sealing-workflow completion must predate the merge. This evidence is a reproducible technical assessment; it is explicitly **not** an authenticated human approval, signed model attestation, or independently authenticated OpenClaw session. 3. **Owner approval:** a GitHub review by the repository Owner `90le` (GitHub user ID `68719118`), recorded as `reviewer_kind=github-user`, must say `APPROVED` for the exact PR head. The Owner may also be the source controller or the person who directed or authored the change, but no other collaborator or source controller can substitute for this v1.0 release authority. No unresolved blocking review, missing required check, skipped check, stale technical-review artifact, non-`PASS` technical decision, or absent exact-head owner approval is acceptable. A Bot-created PR does not change either responsibility.

## Tag, GitHub Release, and artifact gates

Only after the exact merged-main commit passes all prior gates may maintainers create annotated tag `v1.0.0`. Record and verify:

- tag object type `tag`, immutable tag-object ID, peeled commit, tagger identity, GitHub verification result/reason, and exact match to the accepted `main` commit;
- tag-triggered workflow actor/triggering actor and GitHub Release author must be the repository owner `90le` (GitHub user ID `68719118`);
- passing `release-verify.yml` URL for the exact tag, including external-evidence audit and release smoke;
- GitHub Release URL bound to the same tag and commit;
- uploaded release-evidence artifact identity, retention, hashes, and successful download/inspection;
- exact SBOM and source-provenance digests matching the tagged tree;
- no moved/recreated tag and no artifact rebuilt from another commit.

A source document cannot embed the future commit hash or remote URLs of the commit that contains it. Those identities belong in immutable PR/check/tag/Release records or a separately published release evidence record. Their absence means the remote gate is not yet accepted.

### Two-stage machine evidence

The release-evidence Schema has two intentionally non-interchangeable document kinds:

| Kind | May claim | Must not claim |
|---|---|---|
| `TAG_WORKFLOW_EVIDENCE` | exact annotated tag object and peeled commit; local/tag commands; bundled v10, SBOM, provenance and SCM report digests | its own workflow completion, uploaded artifact identity/download, GitHub Release, anonymous install, `ACCEPTED` or `RELEASED` |
| `FINAL_RELEASE_INDEX` | exact PR head and complete required-check set, downloaded exact-head technical review, exact-head GitHub User owner approval, exact accepted-main commit and complete required-check set, tag workflow, artifact ID/URL/digest/retention and download verification, GitHub Release, unauthenticated-public-HTTPS exact-tag install, and every gate `PASS` | any missing, failed, inferred, self-reported, cross-commit or undownloaded gate |

The finalizer accepts a small external JSON request containing repository/release/commit, PR number/head and complete required-check identity, external technical-review identity, GitHub owner-approval identity, accepted-main commit and its complete required-check identity, tag-workflow URL and GitHub Release URL. Those are claims to verify, not proof. It must independently prove that the merged PR targeted this repository's `main`, the accepted commit is the live `refs/heads/main` tip, and the effective `main` required checks match both requested check sets and live results for their exact commits. It then downloads the strict technical-review JSON from the exact private workflow run and verifies its SHA-256/head/workflow commit/runtime/`PASS` decision and verifies the exact-head GitHub User `APPROVED` review. It uses minimum read-only GitHub access only for GET requests, requires one non-expired exact-name tag artifact belonging to the exact tag run, and downloads that artifact rather than trusting metadata. Artifact ID and both API URLs, digest, creation chronology, bundle file set, every SHA256SUMS entry, embedded tag evidence, workflow run/attempt, annotated tag name/object/peeled commit and five required asset digests must agree. Artifact redirects drop the GitHub bearer and are restricted to HTTPS GitHub Actions or Azure Blob object-store host suffixes on the default port.

The five digest-bound assets are:

- `acceptance/v10-host-native-conformance.json`;
- `sbom/agent-team-engineering.spdx.json`;
- `supply-chain/source-provenance.json`;
- `acceptance/github-scm-v10-first-run.json`;
- `acceptance/github-scm-v10-replay.json`.

The final external index uses release-evidence schema `2.1.0` and contains 21 named gates, including separate `technical-review` and `owner-approval` gates. It records the complete required-check set and chronology, technical-review workflow commit/runtime/evidence URL and content digest, owner approval, tagger and GitHub release-owner identities, upload-artifact ID, API URL, archive-download URL, service digest, created/expiry timestamps, derived retention days, actual download timestamp and archive digest, tag-evidence digest, SHA256SUMS digest, and the exact installation boundary fields `unauthenticated_git_transport=true`, `caller_credentials_inherited=false`, `same_uid_filesystem_isolated=false`, `write_isolation=false`, and `external_writes_verified=false`. The last two fields honestly state that the reference run neither isolates nor observes every same-UID filesystem write. An incomplete/mismatched required-check set, post-merge approval/review/PR check, missing technical artifact, non-`PASS` technical decision, missing exact-head owner approval, wrong head/main/tag commit, untrusted release actor, failed workflow, absent Release, expired or duplicate artifact, digest mismatch, missing checksum, skipped download, authenticated/local clone substitution, or any `FAIL`/`NOT_RUN` refuses finalization.

The final index is an observation record produced after live read-only verification, not a self-authenticating proof. It deliberately records `standalone_tamper_evident=false`, `cryptographically_authenticated=false`, and `authenticity_verification=REQUERY_GITHUB_AND_REVERIFY_ORIGINAL_ARTIFACTS`. An attacker who can rewrite the complete JSON can coherently rewrite its digest references; no self-hash can prevent that. Long-term verification therefore requires the original workflow artifacts and request/command evidence plus a fresh GitHub query, or an independently managed signature/transparency log added outside this v1 contract. Structural validation proves internal consistency only and must not be described as authenticating the observer or historical remote facts.

## Unauthenticated public-HTTPS exact-tag installation gate

Run this gate from an independently controlled release worker without a pre-existing checkout. The machine record proves that caller credentials are not inherited by the candidate subprocess environment and that the Git clone uses unauthenticated public HTTPS; it does not prove that the operating-system user or machine has no credentials elsewhere.

1. clone the public repository over unauthenticated HTTPS;
2. fetch and verify annotated tag `v1.0.0` and its peeled commit against the accepted release record;
3. check out that exact tag with a clean worktree;
4. run Factory install into an absent directory, `factory verify`, and Doctor;
5. create and validate a portable team;
6. plan, preview, confirm, apply, verify, preview removal, uninstall, and idempotently verify one disposable host projection without credentials or live host writes;
7. validate the canonical WriterTopology chain and confirm both false boundary fields;
8. record commands, exit codes, environment, commit/tag IDs, artifact digests, and the exact isolation/observation boundary; do not claim that unobserved same-UID writes did not occur.

Testing a local path, authenticated clone, branch head, lightweight tag, or simulated tag does not satisfy this gate.

The reference finalizer executes this gate itself with a literal minimal environment allowlist rather than a filtered copy of the caller environment. It disables global/system Git credential configuration and terminal prompting, clones public HTTPS with `--no-local`, and verifies the tag object and peeled commit. It then performs Factory install/verify/Doctor, portable-team generation, one disposable generic host projection through replay-safe uninstall, and the complete WriterTopology validation. It records `unauthenticated_git_transport=true`, `caller_credentials_inherited=false`, `same_uid_filesystem_isolated=false`, `write_isolation=false`, and `external_writes_verified=false`; a caller-supplied success statement is not accepted as a substitute.

This is a transport and environment-inheritance check, not an OS sandbox or global write monitor. The candidate still runs as the finalizer's user and may read or write paths available to that same UID or inspect readable process data such as `/proc`. For strong release isolation, run the finalizer under a dedicated credential-free user or disposable Runner with filesystem and process isolation; the schema deliberately records `same_uid_filesystem_isolated=false`, `write_isolation=false`, and `external_writes_verified=false` for the reference finalizer.

## Acceptance record rule

The release owner may declare `v1.0.0` accepted only when one external `FINAL_RELEASE_INDEX` maps every gate above to the same accepted commit/tag and contains actual command results, artifact digests, download evidence, and remote URLs. Treat it as an unsigned observation index: archive it together with the original artifacts and rerun the finalizer's read-only checks when authenticity matters. The machine representation uses exact `PASS`, `FAIL`, or `NOT_RUN`; never replace missing evidence with prose such as “expected,” “should pass,” or “verified elsewhere.” Any `FAIL`, `NOT_RUN`, stale external fixture, identity mismatch, undownloaded artifact, missing URL, or missing rollback evidence blocks release completion. The tag-workflow artifact remains an immutable partial input and must never be relabeled or edited into the final index.

## Rollback

The immutable rollback baseline is `v0.9.0`. Keep every v0.9→1.0 instance recovery bundle and every v1-before-rollback rescue bundle until owner acceptance and retention policy permit disposal. Reconcile external Issue/branch/PR effects before retry or rollback. For host projections, run verify and uninstall-preview first; only a proposal-bound v1 lock may use automatic exact-digest uninstall. Preserve and manually reconcile every `LEGACY_UNBOUND` v0.9 installation. Never move a tag, delete a lock or tombstone to force progress, reuse an old approval after topology drift, or treat rollback as authorization to merge or deploy.
