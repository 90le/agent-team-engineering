# ADR-0008：上下文优先团队包、双模式执行与发现插件

- 状态：已接受
- 日期：2026-08-10
- 决策范围：Factory `0.7.0`

## 背景

v0.6已经证明严格蓝图、持久控制面和反馈到经审核Draft PR闭环，但首次访问者容易把Factory理解成只能运行这套Python控制器，也难以快速回答“如何生成几个角色，让Codex、Claude或OpenClaw按同一上下文协作”。如果只保留提示词和Markdown，跨AI理解较容易，却无法确定性验证路径、安全门禁、生成一致性和漂移；如果所有使用都强制运行控制器，则会把简单团队复杂化。

## 决策

1. 以Markdown、严格JSON、Skill和Git作为长期上下文权威，Team Design声明团队、角色、工作流、知识来源、平台目标和人工边界。
2. 提供三个公开preset：`software-lite`、`software-managed`、`custom`。Lite和Custom生成上下文团队包且无需常驻控制器；Managed在同一上下文之下复用v0.6受治理运行时。
3. Python仅承担编译、Schema验证、无覆盖原子发布、SHA-256锁和Managed执行安全属性；不得成为唯一能理解团队含义的载体。
4. 每个平台覆盖层必须携带同一共享上下文；平台文件不得反向授予工具、凭据、批准、merge或部署权限。
5. Custom角色默认只读、只提案，始终保持Lite，直到有独立ADR定义准确的状态机、身份、授权、隔离和恢复映射。
6. 发布一个自包含、无可执行后台组件的发现包：Codex marketplace和plugin manifest、Claude marketplace和plugin manifest，以及OpenClaw可识别的兼容Skill根。插件帮助AI找到Factory并按`AI-START.md`工作，不建立第二套实现。
7. 保留v0.6 CLI和Team Blueprint契约。v0.7新增根命令，不破坏既有实例和参考运行时。
8. Context Lock为每个文件声明`generated`或`user-maintained`。生成的角色、原则、工作流、Skill和平台资产必须与编译器输出一致；项目上下文、架构、知识/决策索引和工作记录可通过Git评审演进，并继续接受路径、UTF-8、大小、符号链接和凭据检查。新增用户文件只允许位于`KNOWLEDGE/`、`DECISIONS/`和`WORK/`。

## 后果

- 普通用户可以只凭Python、Git或一个能读文件的AI创建团队；平台插件是可选入口。
- 同一个团队能在多种AI之间迁移，核心含义不会只存在于某个平台配置或聊天历史。
- Managed继续提供自然语言文件无法保证的批准绑定、幂等、恢复和独立审核。
- Factory必须同时测试上下文层确定性与执行层兼容性，并明确区分“角色声明”和“可执行授权”。
- 插件安装不会自动接线OpenClaw频道、登录模型、授予GitHub写入或修改目标项目；这些仍是采用工程和人工决定。

## 被拒绝的方案

- 只发布提示词模板：不能验证结构、漂移、人工门禁或平台一致性。
- 只发布Python控制器：首次采用成本高，且角色与原则难以被不同AI直接阅读和迁移。
- 为每个平台复制一套团队事实：会造成权限与上下文分叉。
- 让任意Custom角色直接映射外部工具：缺少受审状态、身份和恢复边界，容易产生隐式扩权。
